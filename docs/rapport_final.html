Section 1

Résumé exécutif

1.1 Contexte et enjeux

Ce projet, nommé ETL_Projet_BC, constitue une extension indépendante du projet ETL_Projet existant. Son objectif est de synchroniser automatiquement les données de l'entrepôt de données Gold (PostgreSQL) vers Microsoft Business Central (BC) 26.0 OnPrem, tout en remplaçant la collecte de distances via l'API Google Distance Matrix par un système de tracking GPS en temps réel.

Les données de livraison — clients, articles, en-têtes d'expédition, sessions de distance GPS, lignes d'expédition et lignes e-commerce — sont consolidées dans un Data Warehouse structuré en couches médaillon (Bronze → Silver → Gold) et doivent être disponibles quotidiennement dans l'ERP pour piloter les opérations.

Périmètre technique du projet
Extension AL BC (1 codeunit + 6 tables + 7 pages liste + 6 pages API OData) · 8 workflows n8n · 2 pipelines Apache Hop · 1 script SQL de migration · 8 documents de documentation · Sécurisation webhook GPS par clé API · Synchronisation Gold → BC validée end-to-end (6/6 tables, 100 % records)

Section 6

Réalisation — Infrastructure

6.1 Environnement Docker

L'infrastructure repose sur Docker Compose avec un réseau dédié etl_network (172.18.0.0/16). Tous les services sont isolés et ne communiquent qu'au sein de ce réseau, à l'exception de n8n qui expose son port 5678 sur l'interface hôte (0.0.0.0:5678) pour être accessible depuis le sous-réseau de l'application GPS.

6.2 Migration du schéma Gold

Le script schema_gold_updates.sql applique les transformations nécessaires sur la base data_warehouse_gold :

  • Suppression de l'ancienne dim_distances (schéma origine/destination Google)
  • Création de silver.distance_matrix avec champs VARCHAR pour les données GPS brutes
  • Création de la nouvelle dim_distances avec session_id VARCHAR(50) PRIMARY KEY
  • Suppression de la contrainte FK fact_shipment_lines → dim_date (table supprimée)

7.2 Workflows n8n

L'architecture n8n adopte un modèle hybride avec un orchestrateur (WF-08) qui expose trois déclencheurs et délègue la synchronisation à six sous-workflows indépendants.

WF-08 Orchestrateur (3 déclencheurs) ├─ Webhook POST /webhook/run-gold-to-bc → réponse immédiate 200 ├─ Schedule cron 0 9 * * * → exécution à 09h00 └─ executeWorkflowTrigger → appelable comme sous-WF │ ├─ WF-08A dim_customers → etlCustomers ├─ WF-08B dim_articles → etlArticles ├─ WF-08C dim_ship_headers → etlShipmentHeaders ├─ WF-08D dim_distances → etlDistances ├─ WF-08E fact_ship_lines → etlShipmentLines └─ WF-08F fact_ecom_lines → etlEcommerceLines (LIMIT 10K) │ └─ Merge + Résumé {total_inserted, total_updated, total_errors}

Pattern upsert (WF-08A à WF-08E — clé simple)

POST /ENTITY {payload}
  → 201 Created  : { action: 'inserted' }
  → 409 Conflict : PATCH /ENTITY('key') + If-Match: *  → { action: 'updated' }
  → autre        : { action: 'error', detail: ... }

Pattern upsert (WF-08E et 08F — clé composée)

POST → 409 → GET /ENTITY?$filter=A eq 'x' and B eq y&$select=id
           → récupérer GUID BC
           → PATCH /ENTITY(guid) + If-Match: *

10.3 Business Cases

BC-1 — Élimination de la saisie manuelle

Avant le projet, les données devaient être saisies manuellement dans BC (2h/jour, risques d'erreurs). L'automatisation totale élimine ce poste (14 400 €/an d'économie directe) et réduit le délai de disponibilité des données de "24h en retard" à "disponible à 09h05".

Critères de succès : taux d'erreur < 0,1 % · délai de disponibilité < 30 min après 09h00 · fiabilité > 99 % des exécutions.

BC-2 — Conformité kilométrique et remboursements

Le remplacement de l'API Google Distance Matrix (estimations statiques) par le tracking GPS temps réel apporte des données réelles de trajet. Gains : 4 730 €/an (carburant précis, zéro litige kilométrique) + bénéfices qualitatifs (conformité réglementaire, sécurité conducteurs, indépendance technologique).

Critères de succès : couverture GPS > 95 % des trajets · écart < 5 % avec compteur physique · 0 litige remboursement en 6 mois.

11.3 Enseignements

  • Valider le format source en amont avant tout développement de pipeline de réception
  • Identifier les clés composées BC dès la phase de conception pour anticiper le pattern GET-filter
  • La séparation stricte des projets (ETL_Projet vs ETL_Projet_BC) s'est avérée essentielle pour la présentation
  • L'architecture sous-workflow a rendu les tests très modulaires et facilité le débogage
  • BC OData nécessite PageType = API — les pages Liste ne sont pas accessibles via OData ; à vérifier dès la phase de conception AL
  • Vérifier les contraintes de type BC — Code[10], Code[20], plage de dates licence — avant de mapper les colonnes Gold vers les champs BC
  • Les tests unitaires n8n ne suffisent pas — les erreurs de mapping de champs (400 BadRequest BC) ne se manifestent qu'en test d'intégration end-to-end
Section 12

Conclusion

Le projet ETL_Projet_BC atteint l'intégralité de ses objectifs initiaux. Les six tables Gold sont synchronisées quotidiennement vers Business Central avec une garantie d'idempotence, les données GPS temps réel remplacent les estimations statiques Google Distance Matrix, et l'extension AL fournit un tableau de bord de supervision opérationnel.

L'architecture choisie — médaillon étendue avec webhook GPS, pipelines Apache Hop, orchestrateur n8n hybride et API OData AL — présente plusieurs qualités structurantes :

  • Modularité : chaque table est synchronisée par un sous-workflow indépendant, facilement modifiable ou testable isolément
  • Résilience : une erreur sur un enregistrement ne bloque pas le traitement des suivants ; le schedule assure la récupération automatique
  • Conformité RGPD : les coordonnées GPS ne sont jamais persistées — seules les métriques agrégées transitent vers Gold et BC
  • Sécurité : webhook protégé par clé API, communications BC via proxy NTLM, credentials dans des variables d'environnement chiffrées
  • ROI démontré : retour sur investissement atteint en 3,5 mois, gain net de 60 240 € sur 3 ans

Les axes d'amélioration identifiés pour la suite concernent la pagination incrémentale sur fact_ecommerce_lines (actuellement limitée à 10 000 lignes), la mise en place d'alertes automatiques en cas d'échec de WF-08, et le déploiement optionnel du TLS via nginx pour les communications GPS.
